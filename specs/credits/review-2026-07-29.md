# Credit system review (2026-07-29)

Review of the credit system as merged in PR #13 (`feat: credit system`,
commit `15898a8`) plus the follow-up commits on main. Scope: the full
money path (`credit.repo.ts`, `credit.service.ts`, `usage.ts`,
`credit.schema.ts`), the gates and call sites in apps/api and
apps/worker, and the web client. Usage semantics were verified against
the installed AI SDK packages, not against docs.

Three findings were confirmed. Fixes for all three were applied on
2026-07-29 (uncommitted); the changes are recorded per finding below.

## Finding 1: the gate never checks model pricing, so "fail closed" is not implemented

**Severity: high (silent free usage).**

The PRD (specs/credits/prd.md, "Pricing") promises that a model with no
`pricing`, or a pricing `kind` the charger does not implement, is not
chargeable: "the gate refuses to start a run on it rather than silently
giving it away. This fails closed."

The implemented gates check only `balance > 0`:

- `assertCanSpend` (apps/api/src/services/credit.service.ts)
- `gateCreditSpend` (apps/worker/src/workflow/executors/run-referenced-agent.ts)
- `resolveCreditSpendState` (packages/database/src/repositories/credit.repo.ts)

Nothing pre-run looks at `ai_models.pricing`. With `CREDITS_ENABLED=true`
and a model whose pricing was never seeded (the default, since pricing is
maintained by hand), the run proceeds. `settleCreditUsage` then throws
its "no chargeable token pricing" error, the caller catches and logs it,
and the user is charged nothing. That is exactly the silent giveaway the
PRD forbids.

The comment in `credit.repo.ts` (settlement pricing check) claims "The
gate should have refused the run before it started on a model with no
chargeable pricing". That gate did not exist.

### Proposed change

- Both gates accept an optional `pricing: AiModelPricing | null` input.
  When credits are disabled they still return `null` early with no
  checks.
- When pricing is provided and `pricing?.kind !== 'token'`, the gate
  refuses before any model call. This is a platform configuration
  problem, not the user's fault, so it is not a 402: the API throws a
  distinct internal error, the worker throws a dedicated
  `ModelNotChargeableError` class next to `InsufficientCreditsError` so
  the run-step error text stays distinguishable.
- Call sites pass the model's pricing wherever the model is known at
  gate time: chat (`runChatStream` has `agent.aiModel` loaded),
  `runReferencedAgent` (gate moves after `getAgentById`), the team
  lead (gate moves after lead resolution), and the inline default-agent
  path. The `creditGuard` middleware on `POST /:workflowId/run` keeps
  the balance-only check, since per-node models are unknown at enqueue;
  the worker gates cover those runs per node.
- The `aiModel` query selections gain the `pricing` column where the
  loaded relation did not already include it.

## Finding 2: out-of-credits mid-team-run degrades the run instead of failing it

**Severity: medium (design intent not met, deeper overdraft).**

`InsufficientCreditsError` exists so that "a run refused mid-execution
fails the run with a reason the UI can distinguish from a generic
error" (run-referenced-agent.ts). That works for the agent node, where
the gate throws at the executor's top level.

For team members the gate runs inside the delegate tool's `execute`.
The AI SDK converts tool execution errors into `tool-error` content
parts and the lead's loop continues (`collectStepToolCalls` relies on
exactly that recovery path). So when the balance hits zero mid-run, the
lead sees failing delegate tools, may retry them, and keeps burning its
own tokens. Those lead tokens still settle, deepening the overdraft.
The run then completes "successfully" with degraded output.

### Proposed change

In `team.executor.ts`, an `AbortController` is created per team run and
its signal passed to the lead's `generateText`. The delegate tool wraps
`runReferencedAgent`: when it throws `InsufficientCreditsError` (or
`ModelNotChargeableError`), the error is captured in a shared variable,
the controller is aborted, and the error is rethrown inside the tool.
After `generateText` rejects due to the abort, the captured credit
error is rethrown so the node fails with the right message. Any other
rejection with no captured error is rethrown as-is. The lead's aborted
partial run is deliberately not settled, matching the v1 policy that
failed and aborted runs charge nothing (PRD, "Non-goals").

## Finding 3: CREDIT_MARKUP_BPS parsing swallows bad values

**Severity: low (config footgun on a value that multiplies every charge).**

`packages/config/src/services/config.service.ts` parses the env var as
`Number(val) || 15_000`. An explicit `CREDIT_MARKUP_BPS=0`, or any typo
that parses to `NaN`, silently becomes the 15000 default. The per-model
override in `computeCharge` handles this correctly with `??`.

### Proposed change

Validate instead of falling back: absent defaults to 15000, an invalid
or non-positive value fails schema validation at startup with a clear
message (`z.coerce.number().int().positive().default(15_000)` shape,
with empty-string env values normalised to undefined first).

## Minor notes (not fixed)

- `/credit/usage` accepts an unbounded `limit`. This comes from the
  shared `paginationSchema` and is an app-wide pattern, not a credits
  bug. A cap would be cheap.
- The verification comment in `packages/ai/src/usage.ts` pins exact
  package versions (`ai@7.0.34` etc.) that went stale when the
  pkg-upgrade commit bumped to 7.0.37. The `VERIFIED_PROVIDERS` canary
  only fires on unknown providers, not on SDK upgrades, so the
  cache-inclusive `usage.inputTokens` guarantee should be re-checked on
  major bumps. Verified for the currently installed version:
  `inputTokenDetails` / `outputTokenDetails` are non-optional objects in
  ai@7.0.37, so the field accesses in `normalizeUsage` are safe.
- The grant script hardcodes `kind: 'grant'` even for negative amounts.
  `adjustment` exists in the ledger-kind enum and would read better.
  Cosmetic.
- `Number(balanceMicroCredits)` in the balance response loses precision
  only beyond roughly 9 billion credits. Fine in practice.

## What holds up well

- The settlement transaction: balance debit via `UPDATE ... RETURNING`
  for row-level serialisation, usage event and ledger row in the same
  transaction, and the unique `idempotencyKey` violation rolling back
  the whole thing. A retry can never double-charge or orphan a row.
- Pricing is snapshotted from a read inside the same transaction, so
  the recorded `unitPrices` are guaranteed to be what the charge was
  computed from.
- The money path is bigint end to end, with `ceilDiv` as the single
  rounding point. The grant script hand-parses decimals to avoid float
  drift.
- The charged/actual cost split (`costNanoUsd` vs `actualCostNanoUsd`)
  keeps margin data server-side, and the response DTO deliberately
  never leaks it.
- The 402 path is wired consistently across HTTP and WS, sharing one
  "out of credits" message in the web client.
- Gating and settling are coupled to `CREDITS_ENABLED` in all three
  call sites (chat, workflow, team), so accounts that were never
  checked can never be charged.
- All three new tables are registered in `relations.ts`, and usage
  rows denormalise provider/model/display name so history survives
  model renames and deletions without joins.
