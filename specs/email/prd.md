# Email Client (PRD)

> **Status: implemented** (2026-08-14, branch feat/email-client). Built by
> subagent team, live-tested (connect, seed sync, manual sync, compose),
> covered by the apps/api email test suite (test/email/, 73 tests). Known
> deferrals: draft-run credits (needs CreditUsageFeature extension),
> thread-participants merge on incremental sync, Gmail drafts write-back.

A Gmail-backed email client inside `apps/web`, in the spirit of Superhuman
and the open-source Inbox Zero / Zero (Mail0) projects. Two AI features sit
on top of a regular client: automatic categorization of incoming mail, and
AI reply drafts generated by a configurable agent. Drafts are always
reviewed by the user before sending; nothing is auto-sent.

## Goals (v1)

- Connect exactly one Gmail account per user (OAuth, `gmail.modify` scope).
- Work as a regular email client: read threads, compose, reply, reply-all,
  forward, archive, trash, star, mark read/unread. All writes go through the
  Gmail API so state stays consistent with the user's real mailbox.
- Auto-categorize incoming mail into user-configurable categories (seeded
  defaults), classified by a small LLM on ingest.
- Auto-draft replies via a configurable agent, triggered only for:
  - categories the user has flagged "auto-draft on", and
  - senders on a user-maintained email list.
- Manual "Draft with AI" button on any thread. Uses the account's default
  agent, overridable per use via a dropdown. Same job as the auto trigger.
- Attachments: view and download on received mail; attach files when
  composing (upload or pick from the media library).
- Gmail labels shown read-only on threads, filterable, not editable.
- Search proxies Gmail's `q=` search operators instead of local full-text.
- Classify and draft calls account credits through the existing credit
  service.

## Non-goals (v1)

- Any non-Gmail provider. Microsoft (Graph API) is planned later, so v1
  hides Gmail behind a provider interface (see "Future directions"), but
  only the Gmail implementation ships. IMAP/SMTP stays out entirely.
- Agent email tool. Planned later; v1 only keeps the service layer
  tool-callable (see "Future directions").
- Multiple accounts per user.
- Full mailbox mirror / offline support. See "Sync model" below.
- Push sync via Google Pub/Sub `watch()`. Polling only; the sync job is
  shaped so a Pub/Sub trigger can later enqueue the same job.
- Writing categories back to Gmail as labels; editing Gmail labels at all.
- Writing AI drafts into Gmail's drafts folder. Drafts are local-only.
- Auto-send. Every AI draft requires user review.
- Local full-text search over bodies.

## Sync model: metadata index + lazy body persistence

The DB stores one lightweight row per message: Gmail message id, thread id,
sender, recipients, subject, snippet, date, unread/starred flags, label ids,
plus our columns (category, needs-reply, draft reference).

Bodies are persisted lazily, not proactively mirrored. Email bodies are
immutable, so storing them adds no sync burden beyond purge-on-delete;
only flags/labels/existence change, and the index tracks those anyway.

- The first time a body is fetched for any reason, the parsed text/HTML is
  stored on the message. The classifier touches every new incoming
  message, so from connection day forward every new message has its body
  persisted at classify time, with zero extra API calls.
- One-time seed on connect: the most recent ~50 inbox threads are imported
  (metadata + bodies, since they are fetched anyway) so the client is not
  empty on day one. Beyond that, no backfill of pre-connect history:
  opening an older thread fetches live from Gmail and persists lazily on
  that first view.
- Draft agent and thread view read stored bodies when present, fall back
  to live fetch otherwise. One MIME-parsing path, at fetch time.
- Attachments stay fetch-on-demand (streamed from Gmail, never stored).
- The poller applies `history.list` changes (new mail, read/unread,
  archive, trash, label changes, deletions) so the index does not drift;
  deletions purge the local row including the stored body.
- Mailbox actions from our UI write to Gmail and update the local row
  immediately, so the UI never waits for the next poll.

This keeps thread opens instant for all post-connect mail, parses each
message once, retains what the classifier saw for debugging, and gives
future features (voice matching, agent email tool) local text to work
with, without a backfill project or a full-mirror sync job.

## Content pipeline

Markdown is the canonical representation for everything: LLM input, LLM
output, user reading, and user editing. HTML appears only at the two
edges: at ingest as the source turndown converts from, and at send as the
wire format the editor emits. The web app never parses, sanitizes, or
renders received HTML.

- **Ingest:** `textBody` is derived canonical markdown, computed once at
  persist time: turndown conversion of the HTML part when present, else
  the `text/plain` part. Since markdown is also the display
  representation, conversion quality matters (links, images, tables must
  survive). `htmlBody` is stored raw but not consumed by the UI; it is
  kept as the conversion source, enabling re-processing or a future
  "view original" toggle. LLMs never see raw HTML.
- **LLM reading:** one shared thread-to-prompt formatter in `@repo/mail`
  (used by classify, draft, and the future agent email tool): messages
  oldest to newest with From/Date/Subject, markdown bodies with quoted
  reply chains stripped (`gmail_quote` blocks, "On ... wrote:" trailers),
  token-budgeted by dropping oldest messages first.
- **LLM writing:** the draft agent outputs a markdown reply body only. No
  subject line, no quoted history, no invented signature; anything
  structural is appended by the system, not the model.
- **User reading = user editing:** the thread view renders each message's
  markdown `textBody` through `@repo/editor` (read-only), exactly like
  every other editor usage in the app. Accepted tradeoff: designed
  newsletter/marketing layouts render as plain structured markdown.
- **User writing:** compose and draft editing hydrate markdown into
  `@repo/editor`; on send the client emits the editor's HTML + text
  alternative (see Web section).
- **Reply quoting:** quoted history lives in the composer as markdown. On
  reply (manual or from an AI draft) the client appends "On DATE, NAME
  wrote:" plus the replied-to message's markdown as `> `-quoted lines
  below the reply body, visible and editable like everything else. The
  editor's send conversion carries it to HTML; the API never appends
  quotes server-side.

## Architecture

### Auth and account connection

- **Not part of signup.** The Google sign-in provider keeps its plain
  openid/profile/email scopes. Gmail access is granted through the existing
  account-linking flow (`useUserSocialAccounts.ts` on `/account`, backed by
  better-auth `linkSocial()` with no custom endpoints), the same pattern
  already used for LinkedIn/Microsoft linking.
- The email client's "Connect Gmail" action calls `linkSocial()` with an
  additional `scopes: [gmail.modify]`, so only users who opt into the email
  client ever see the sensitive-scope consent screen.
- Google only issues a refresh token on a consenting grant: the Google
  provider config needs `accessType: 'offline'` and `prompt: 'consent'`
  for this flow. Access/refresh tokens live in better-auth's `account`
  table; a small token service handles refresh.
- `email_accounts` row per user: `provider` enum (v1: `gmail` only), email
  address, opaque `syncCursor` (Gmail: `historyId`; Graph later: delta
  token), default draft agent id, sync state. One row per user enforced.
- Google treats `gmail.modify` as a sensitive scope. The OAuth app runs in
  testing mode, which is fine for this showcase app.

### Database (`packages/database`)

New tables, all registered in `schema/relations.ts`:

- `email_accounts` — per-user connection, provider, cursor, default agent.
- `email_threads` — thread id, subject, last-message date, denormalized
  participants/snippet for the list view.
- `email_messages` — metadata index row (see "Sync model").
- `email_message_bodies` — lazily persisted parsed body per message, 1:1,
  purged with the message row: canonical markdown (`textBody`, the only
  representation the UI and LLMs consume) + raw HTML (`htmlBody`, stored
  as conversion source only, never rendered).
- `email_categories` — per-account: name, natural-language description
  (fed to the classifier), color, `autoDraft` flag. Seeded defaults on
  account connect.
- `email_auto_draft_senders` — per-account list of sender addresses that
  always trigger auto-draft, independent of category.
- `email_drafts` — local AI drafts: thread ref, agent used, editor content,
  state (generating / ready / discarded / sent).

### Worker jobs (`@repo/queue` + `apps/worker`)

Three processors, following the existing queue-name/DTO/processor pattern:

1. **email-sync** — cron fans out one job per connected account. Calls
   `history.list` from the stored cursor, upserts metadata rows, applies
   flag changes, enqueues classification for new messages. Interval from
   `EMAIL_SYNC_INTERVAL` (`@repo/config` env var, default 5 minutes).
2. **email-classify** — fetches the message body, persists it (see "Sync
   model"), prompts a small model (Haiku-tier) with the account's category
   set, writes the category to the message row. If the category has
   `autoDraft` on, or the sender is on the auto-draft list, enqueues
   email-draft.
3. **email-draft** — runs the selected agent (account default, or the agent
   chosen in a manual trigger) with the thread history as context (stored
   bodies, live fetch for gaps). Stores the result as an `email_drafts`
   row. Surfaced in the UI for review.

Manual "Draft with AI" hits an API endpoint that enqueues the same
email-draft job with an optional agent override.

### API (`apps/api`)

Thin controllers, logic in an `email.service.ts`. Provider access goes
through a `MailProvider` interface (sync-from-cursor, get thread with
bodies, send, mailbox actions, search, attachment streaming) with one v1
implementation, `gmail.provider.ts`, wrapping the Gmail API + token
refresh. `email.service.ts` and the worker jobs only talk to the
interface, never to Gmail directly. The Gmail wrapper is a hand-rolled
fetch client, not `@googleapis/gmail`; see
[gmail-client-decision.md](./gmail-client-decision.md) for the reasoning
and tradeoffs. Endpoints:

- Account: connect status, disconnect, settings (default agent, categories,
  auto-draft sender list), manual "Sync now" trigger (enqueues the same
  email-sync job the cron fans out, deduped per account via the BullMQ
  jobId).
- Threads/messages: list from local index (filter by category, Gmail
  label, system folder), thread detail (stored bodies, live fetch +
  persist for gaps), search (Gmail `q=` proxy).
- Actions: archive, trash, star, read/unread (Gmail write + local update).
- Compose/send: send via Gmail API with `In-Reply-To`/`References` headers
  for replies; attachment upload; attach from media library.
- Drafts: list, trigger manual draft, edit, discard, send.
- Attachments: download proxy streaming from Gmail.

### Web (`apps/web`)

Three-pane client: sidebar (system folders, categories, Gmail labels,
auto-draft settings), thread list, thread view. Reply/compose uses
`@repo/editor` with its full formatting set. The editor is markdown-native:
AI drafts (LLM markdown output) hydrate straight into it, and on send the
client emits the editor's HTML plus a text alternative. Markdown-to-HTML
conversion lives client-side in the editor only; the API passes
`{ html, text }` through to the provider and never renders markdown. AI drafts appear inline on the thread with edit / discard /
send. Category and sender-list management lives in the email settings page.

## Config

- `EMAIL_SYNC_INTERVAL` — poll interval, default 5 minutes.
- Gmail OAuth client id/secret reuse the existing Google OAuth config.

## Future directions (design for, ship later)

### Microsoft / other providers

Second provider: Microsoft via the Graph API. Graph maps cleanly onto the
`MailProvider` interface: delta queries replace `history.list` (hence the
opaque `syncCursor`), `$search` replaces Gmail `q=`, Outlook
folders/categories replace labels for the read-only display. What v1 does
to prepare, and nothing more:

- `provider` enum + opaque cursor on `email_accounts`.
- Provider ids (message, thread, label) stored as opaque strings.
- All Gmail calls behind `MailProvider`; no Gmail types outside
  `gmail.provider.ts`.
- Account connection already goes through the shared link-account flow,
  which supports Microsoft today; a Microsoft mail account is the same
  `linkSocial()` call with Graph mail scopes.

Not prepared for: providers without threading or without a labels concept.
IMAP stays rejected.

### Agent email tool

An email tool in `@repo/ai` that an agent can be configured with, bound to
a specific connected email account chosen in the agent's tool config.
Candidate capabilities: search/read threads, create a draft, send. To
settle when it's built:

- Permission granularity (read-only vs draft vs send) per tool config.
- Whether an agent may send autonomously or only create drafts for review,
  mirroring the no-auto-send rule of the client itself.
- Account authorization: the tool config can only reference accounts owned
  by users who can already access that agent's workspace.

V1 preparation: all mailbox operations live in `email.service.ts` /
`MailProvider`, callable without an HTTP request context, so the tool can
reuse them directly.

## Open questions

- Workspace interplay: the account is per-user, but agents are workspace
  resources. The agent picker likely lists agents from workspaces the user
  belongs to. Decide when building the settings UI.
- Voice matching: feeding the user's past sent mail to the draft agent via
  the existing pgvector retrieval pattern. Nice later, not v1.
- Cursor expiry: Gmail `historyId` can expire on long-idle accounts; the
  sync job needs a full-resync fallback path. Handle during implementation.
