# Better Auth 1.8 gap analysis

Reference, not a PRD. Written 2026-10-16 against `v1.8.0-beta.0` (commit `be781d5`). npm `latest`
was 1.7.10 at the time; the repo resolves 1.7.7. Input for a later `better-auth-1.8-upgrade-prd.md`
once 1.8 ships stable. Re-check the stable changelog against this list before writing the PRD.

Scope: which 1.8 breaking changes affect our better-auth setup, with focus on the OAuth provider
and MCP server. Also how they relate to
[OAuth and MCP hardening](../security/oauth-mcp-hardening-prd.md).

## Our setup (1.7.7)

- `packages/auth/src/server/auth.ts`: `admin`, `lastLoginMethod`, `organization`, and behind
  `config.mcpEnabled`: `jwt()`, `mcp()` (no DCR), `cimd()` with the `MCP_ALLOWED_CLIENT_IDS`
  allowlist. Social providers Google, Microsoft, LinkedIn. No email/password, no device grant, no
  `pairwiseSecret`, `cookieCache` off.
- MCP requests: `requireMcpAuth` verifies the JWT locally (`apps/api/src/services/mcp.service.ts`).
  We never call `/oauth2/revoke`, `/oauth2/introspect` or `/oauth2/userinfo`.
- Revoking a connection deletes better-auth rows directly via Drizzle (`oauthAccessToken`,
  `oauthRefreshToken`, `oauthConsent`): `packages/database/src/repositories/mcp.repo.ts` and
  `revokeMcpAccess` in `organization.repo.ts`. This couples us to the plugin's table shape.
- The OAuth provider tables are hand-written Drizzle in
  `packages/database/src/schema/oauth-provider.schema.ts`, not generated by the better-auth CLI.
- Consent hand-off: the provider redirects to `/oauth/consent` with the full authorize query,
  signed (`sig`, `exp`) by `signParams`. `login.vue` forwards `window.location.search` back to
  `/auth/oauth2/authorize`. `consent.vue` reads `client_id` from the query.

## Breaking changes vs. our code

| Change                                                                          | Impact      | Action                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `oauthClient.sectorIdentifier` column (#11650, pairwise)                        | **Must do** | Optional `string` field in the beta's `oauthClient` schema. Add `sector_identifier text` to `oauth-provider.schema.ts`, `db:generate`, deploy the migration before the bump. Otherwise CIMD client writes likely fail. No `pairwiseSecret`, so `sub` stays public. |
| RFC 7009/7662 revocation, introspection, userinfo, refresh errors (#11796)      | None        | We call none of these endpoints. No tests assert their errors. Claude calling revoke gets the RFC behavior (200 for unknown tokens).                                                                                                                               |
| Repeated form params rejected, malformed `resource` → `invalid_target` (#11746) | Low         | Only affects malformed client requests. `resource` may still repeat. Watch Claude Desktop connects after the bump.                                                                                                                                                 |
| No consent record for empty scopes (#11610)                                     | None        | Our scopes are `mcp` and `offline_access`.                                                                                                                                                                                                                         |
| Device approval moved into authorize/consent, `interactionRequests` (#11610)    | Indirect    | We use neither the device grant nor custom approval extensions. Device fields belong to the device plugin's schema. But the consent flow internals changed: regression-test the full MCP flow (see below).                                                         |
| Device-code concurrency and `expired_token` polling (#11772)                    | None        | Device grant not used.                                                                                                                                                                                                                                             |
| Sign-up emails and OAuth session caching after DB work (#11751)                 | None        | No `sendVerificationEmail` / `onExistingUserSignUp`, `cookieCache` off. `databaseHooks.user.create.after` unaffected.                                                                                                                                              |
| `DeviceAuthorizationGrant` interface rename (#11610)                            | None        | Not used.                                                                                                                                                                                                                                                          |

Non-breaking items worth knowing: the CIMD fix for documents that declare at least one supported
grant (#10731) helps us. Token exchange, front-channel logout, acr/amr claims, CIBA and the DPoP
polling fix are not needed today.

## Relation to the OAuth/MCP hardening

None of the four hardening items needs a better-auth change, and none depends on 1.8. Keep them
separate from the upgrade.

- Item 1 (audit trail): our own tables only.
- Item 2 (mail tokens): updates better-auth's `account` row directly. Google revoke can use the
  access token from `auth.api.getAccessToken`, so we never decrypt the refresh token ourselves.
- Item 3 (LinkedIn): config only. Open: does `linkSocial` with extra scopes merge them into
  `account.scope`?
- Item 4 (consent page): reads `redirect_uri` from the signed query. That query shape is the one
  thing 1.8's consent restructuring could change. Re-check after the bump.

## Upgrade checklist (for the later PRD)

1. Add `sector_identifier` to `oauthClient`, generate and apply the migration.
2. Bump `better-auth`, `@better-auth/oauth-provider`, `@better-auth/mcp`, `@better-auth/cimd`
   together (plus `packages/testing`).
3. Diff the beta's plugin schemas against `oauth-provider.schema.ts` for anything else new.
4. Check that the direct deletes in `mcp.repo.ts` / `revokeMcpAccess` still cover every table
   that holds MCP grants.
5. End-to-end with Claude Desktop: login, consent (including `redirect_uri` in the query),
   token, refresh, revoke in settings, reconnect.
6. `pnpm test:api` and `pnpm check-types` (the `as unknown as ReturnType<typeof betterAuth>` cast
   in `auth.ts` may hide type drift).
